# アプリのリポジトリの履歴からノートを消して公開できる（#35）

## なぜ

アプリのリポジトリ（md-leaf）をポートフォリオとして公開したい。#34 で main から `content/` はなくなったが、過去のコミットと、GitHub の PR（#11・#26・#33・#36 の差分）に、非公開のノートの中身が残っている。そのまま公開すると、誰でもノートを読めてしまう。

## 影響する今の仕様

- アプリの動きは変わらない（`docs/specs/` は変えない）
- 変わるのはリポジトリの置き場所と、それにつながる設定：`README.md`（リポジトリの URL が出てくるところ）、`docs/vault.md`（Deploy Hook を作り直すときの手順）
- 新規：`docs/publish.md`（公開の手順と、やったことの記録）

## 使う場面

1. 採用の担当者が、ポートフォリオに書いた `github.com/tsubokura14/md-leaf` を開く。コード・`docs/`・コミットの履歴（開発の流れ）は読めるが、どのコミットを開いても `content/` のノートはない
2. 本人が PC の Obsidian でノートを直し、保管庫に push する。公開する前と同じく、数分で本番に反映される
3. 本人がこれまでどおり `/dev-fix` で次の Issue を進める。公開したリポジトリで PR を出し、CI が通り、マージすると本番に出る

## 受け入れ条件

- 公開したリポジトリのどのブランチ・どのコミット・どの PR からも、`content/` のファイルが読めない
- 公開したリポジトリに、秘密の値（鍵・トークン・許可するメールアドレスの実際の値）が、今の版にも履歴にもない
- 公開したリポジトリに、main だけがある（作業ブランチを持ち込まない）
- 本番の URL は変わらず、ログイン・ノートの表示が公開の前と同じに動く
- 保管庫の main に push すると、公開の前と同じく本番に反映される
- 公開したリポジトリで PR を出すと CI が動き、マージすると Vercel が本番にデプロイする
- テンプレートとのつながり（`.template-version`、remote `template`）が、新しいリポジトリでも使える
- main への直接の push が、GitHub の側でも止まる（公開すると無料でブランチの保護が使える）
- 取り消せない操作（push・公開・削除）は、手順書のとおり1つずつ、人が承認してから行う

## 画面

画面は変わらない。

## やらないこと

- アプリのコードの変更
- 保管庫（`learning-vault`）の公開
- ポートフォリオとしての `README.md` の書き直し（公開したあと、新しいリポジトリの別の Issue にする）。この作業では、リポジトリの URL など、公開で変わるところだけを直す
- テンプレートのリポジトリの変更（`docs/template-harvest.md` の記録の直しは、テンプレートの側の作業）

## 設計

## AIが決めたこと

- プロトタイプは作らない。理由：画面が変わらない
- 履歴の書き換えは、今の作業フォルダではなく、別のフォルダに取った新しいクローンで行う。理由：今の作業フォルダ・worktree・ほかの会話の作業を壊さない。比べた案：今のフォルダで書き換える（失敗したときに戻すのが大変）
- 書き換えには `git filter-repo`（`pip install git-filter-repo`）を使う。理由：Git の公式の文書が `git filter-branch` の代わりに勧めている。比べた案：`git filter-branch`（入れなくてよいが、遅く、消し残しの落とし穴が多い）、BFG（Java が要り、パスでの指定が弱い）
- 消すのは `content/` だけにする（「調べたこと」のとおり、ほかに公開して困るものはない）
- 新しいリポジトリには main だけを入れ、タグ・ほかのブランチは入れない。理由：古いブランチには書き換えていないコミットがあり、持ち込むと消し残しになる
- コミットメッセージの `(#36)` などの番号は書き換えない。理由：書き換えると開発の流れと古いリポジトリの PR の対応が分からなくなる。代わりに `docs/publish.md` に「#番号は古いリポジトリ（`md-leaf-archive`）の PR」と書く
- 新しいリポジトリの設定は `scripts/setup-github.sh` で行う（Squash だけ・マージ済みのブランチを消す・main の保護・push protection）。公開すると、今は使えないブランチの保護と push protection が無料で使える
- 公開の前に、書き換えたクローンで `git log --all -- content/` が空であることと、`npm run lint`・`npm test` が通ることを確かめる
- 新しいリポジトリへの切り替えのあと、手元は新しいリポジトリを別のフォルダにクローンして作業を続ける。古い作業フォルダは、人が確かめてから消す（消すのは人の承認のあと）

- この PR は手順書と文書の直しだけにし、取り消せない操作は、この PR を人がマージしたあとに、`docs/publish.md` のとおり1つずつ承認をとって行う。理由：書き換える元を「この PR を取り込んだ main」にすれば、手順書と仕様ファイルが新しいリポジトリの履歴に入る。先に操作すると、この PR が古いリポジトリに取り残される。比べた案：操作を終えてから記録だけの PR を出す（手順書を人がレビューする前に取り消せない操作が始まる）
- PR の本文は `Closes #35` ではなく `Refs #35` にする。理由：マージした時点ではまだ公開していないので、Issue を閉じるのは手順の最後（`docs/publish.md` の「記録の PR」のあと）にする
- 新しいリポジトリの main への最初の push は、人が打つ。理由：AI は main に push しない決まり（`AGENTS.md`）。書き換えたクローンでは `.githooks` を有効にしないので、フックでは止まらない
- 古いリポジトリの名前を変えたらすぐに、手元の古いクローンの `origin` を `md-leaf-archive` に向け直す手順を入れる。理由：新しいリポジトリを同じ名前 `md-leaf` で作ると、古いクローン・worktree の `origin`（`.../md-leaf.git`）が新しいリポジトリを指し、書き換えていない古いブランチ（ノート入り）を誤って push できてしまう（`.githooks/pre-push` は新しいブランチの push を止めない）
- 公開は、新しいリポジトリを非公開で作って push し、GitHub の上でノートがないことと本番が動くことを確かめたあとにする。理由：公開だけは取り返しがつかない（一度でも読まれたら戻せない）。非公開のうちなら、間違えてもリポジトリを消して作り直せる
- 手元は、古い作業フォルダ `md-leaf` を `md-leaf-archive` に名前を変え（`git worktree repair` で worktree のつながりを直す）、新しいリポジトリを `md-leaf` にクローンする。理由：ほかのリポジトリと同じく、フォルダの名前とリポジトリの名前をそろえる
- 古いリポジトリの Issue は持ち込まない（今開いているのは #35 だけで、手順の最後に閉じる）。GitHub は、非公開から公開のリポジトリへ Issue を移せない
- 確かめるコマンドは `docs/publish.md` に書き、スクリプトにはしない。理由：一度しか使わない。手順と結果を同じ文書で読めるほうが、人が1つずつ承認しやすい
- 手順を書く前に、作業フォルダの外（一時フォルダ）に main を新しくクローンして、書き換えと確かめを一度試した（2026-11-14、main は `6b1dbf4`）。結果：20 コミットが 19 になる（`content/` だけを変えた「ノートを content/ に追加する (#26)」が空になって消える）。最後の版の中身は、main から `content/` を除いたものと一致。`content/` にあったファイルの中身（121 個）のうち、残ったのは空のファイルの中身（`e69de29`。どのリポジトリにもある、長さ0のもの）だけ。トークンの形の文字列なし、`.env` は `.env.example` だけ、メールアドレスは noreply とテスト用の `@example.com` だけ
- `git filter-repo` は手元の道具で、アプリには入れないので、`docs/libraries/` には書かない。手元では `pip install --user` で入れ、コマンドの置き場所が PATH にないことがあるので、`python -m git_filter_repo` で呼ぶ
