# 決まりの置き場所と流れ

## 決まりを層に分ける

今の形：

- `AGENTS.md` には、毎回要る大枠だけを書く。`CLAUDE.md` は `@` で取り込むだけ
- 1つのコマンドの中だけで要る手順は、手順スキル（`/dev-fix` など）に書く
- いくつかの作業で要る細かい決まりは、知識スキル（`user-invocable: false`）に書き、AIが作業に合わせて読む
- `.claude/rules/` は、`paths:` のファイルを触ったときに、どのスキルを読むかを伝えるだけにする。例外は、テンプレートのリポジトリだけで使う `template-notes.md`（`paths:` なしで、このフォルダを読ませる。下の「判断の理由は、このフォルダに書く」）

理由：2026年10月の作り直し（Issue #31〜#34、PR #35〜#38）の前は、決まりが多くの場所に積み重なり、大枠が埋もれて、決まり同士が食い違っていた。使う側では原因の分かりにくい不具合が出ていて、流れが重すぎることと、フックの誤作動が挙がった。AIには大枠だけを持たせ、細かいことは段階的に読み込ませる。

決まりを足すときは、足すだけでなく、まとめる・消すことも考える。足し続けると、作り直しの前と同じことが起きるため。

## 流れは2つ

今の形：`/dev-fix` と、`/dev-proto` → `/dev-build` の2つ。機能の仕上げ（今の仕様・設計への反映）は、別のコマンドにせず `/dev-build` の最後に行う。

2026年10月の作り直しのときに決めた。作り直しのきっかけの1つが、流れが重すぎることだった。

### 1機能 = 1PR、実装はタスクごとのサブエージェント

今の形：`/dev-build` が、設計・タスク分け・実装・仕上げ・PR までを止まらずに行い、機能を1つの PR にする。タスクはブランチの中のコミットで分ける。実装はタスクごとにサブエージェント `implementer` が新しい文脈で行い、`/dev-build` の会話は進行役になる。

理由：人の確認を最小限にする作り直し（Issue #1〜#7）。それまでは仕様PRと、タスクごとの PR があり、人がタスクの数だけコマンドを打ってマージしていた。人の判断を「プロトタイプでの合意」と「確認とマージ」の2回にするには、間の PR とコマンドをなくす必要がある。

前提：PR が大きくなるので、レビューは受け入れ条件の表・AIが決めたこと・タスクごとのコミットで追う。大きすぎる機能は `/dev-proto` の段階で Issue を分ける。

サブエージェントにした理由：

- 会話を区切る代わり。プロトタイプを触った会話の記憶や、長くなった会話を実装に持ち込まない
- プロトタイプのフォルダを読ませない守りを、フック（guard.mjs の `implementer`）で効かせられる（[guards.md](guards.md#implementer-は、リポジトリの外をすべて止める)）

とらなかった案：

- タスクPRを残し、AIが続けて出す：マージが PR の数だけ要り、前のタスクPRがマージされるまで次に進めない（PR を積み重ねると、Squash merge のたびに作り直しになる）
- 1つの会話で全部を実装する：タスクが増えると会話が長くなり、前提を忘れる。プロトタイプの記憶も残る

### 仕様はプロトタイプの会話で決める

今の形：`/dev-proto <Issue番号>` が、仕様の下書き・質問・プロトタイプ・技術の確認表までを1つの会話で行い、合意を人の判断の1回目にする。質問は、AIが推す答えを添えて1回にまとめる。画面が変わらない機能では、プロトタイプを作らずに仕様だけで合意する。

理由：人の確認を最小限にする作り直し（Issue #1〜#7）。それまでは `/dev-spec` で仕様を質問で決め、会話を区切って `/dev-proto` でプロトタイプを触り、また会話を区切って `/dev-spec` に戻っていた。言葉の質問より、触って直すほうが早く決まり、人のコマンド入力も減る。

とらなかった案：

- `/dev-spec` で仕様を決めてから、必要なときだけプロトタイプ（作り直し前の形）：質問のやり取りと会話の区切りが多い
- 仕様もプロトタイプもAIが作り、人は最後の PR だけを見る：何を作るかは人が決める（decisions スキル）。作ったあとで違うと分かると、作り直しが大きい

### 合意済みの機能は `/dev-run` で続けて作る

今の形：`/dev-run <Issue番号...>` が、合意済みの機能を `/dev-build` と同じ手順で順に作る。1つの機能で人に聞くことが出たら、その機能だけを止め、質問を仕様ファイルの「決まっていないこと」に書いて push し、ほかの機能へ進む。「先に要る機能」がまだ main にない機能は飛ばす。同じフォルダで、ブランチを切り替えて1つずつ作る。

理由：人の確認を最小限にする作り直し（Issue #1〜#7）。プロトタイプでの合意は人がいるときに済ませ、作るのは人がいないときにまとめて行えるようにする。人がいないので、1つの機能で止まって全体が止まらないようにする。

とらなかった案：

- 機能ごとに `git worktree` でフォルダを分け、並べて作る：サブエージェントからはサブエージェントを起こせないので、並べても進行役は1つになり、速くならない。implementer のフックが見る「作業中のリポジトリ」、画面を撮るサーバーのポート（foundation スキル）など、フォルダごとに合わせるものが増える。1つずつ作るなら、ブランチを切り替えれば足りる
- まだマージされていない機能のブランチの上に、次の機能を積み重ねる：Squash merge で取り込むたびに、上の機能のブランチを作り直すことになる

### 立ち上げは `/dev-start` の1つの会話と、1つの PR

今の形：`/dev-start` が、GitHub の設定・目的・雰囲気と主な画面・技術・Issue の分け方を1つの会話で決め、「開発を始められる」の仕様ファイルまで書く。`/dev-build` が土台を作り、立ち上げで決めたもの（`docs/overview.md`・`docs/ui.md`・合意した画面・仮のトークン）と一緒に1つの PR にする。

理由：人の確認を最小限にする作り直し（Issue #1〜#7）。それまでは S1〜S4 に分かれ、人が `docs/overview.md` を書き、スクリプトを実行し、画面の PR をマージしてから、技術を `/dev-spec` で決めていた。技術は画面と主な機能が決まった時点で選べるので、同じ会話で決める。

とらなかった案：

- 画面の PR を先にマージしてから土台を作る（作り直し前の形）：マージが2回になる。土台の PR が来るまで、ほかの機能は作れないので、分けても先に進めるものがない

## 人とAIの判断の分け方は decisions スキルの1か所に書く

今の形：何を人が決め、何をAIが決めて書くかは decisions スキルにだけ書く。`AGENTS.md` の「止まって聞くとき」と `/dev-fix` の「機能の流れにするもの」は、そこを指す。

理由：人の判断を「プロトタイプでの合意」と「確認とマージ」の2回にまとめる（Issue #1〜#7 の作り直し）。それまでは「推測で進めない」が広く、細部でも止まって聞いていた。止まらずに進めるには、AIが決めてよい範囲をはっきりさせる必要がある。作り直しの前は、影響の大きい変更の一覧が `/dev-fix` にだけあり、技術の選び方は foundation スキルにあった。

前提：分ける基準は「あとから変えるのにどれだけかかるか」と「お金・データ・外部に関わるか」。人が決めるものの漏れは、プロトタイプの最後に埋める「技術の確認表」で見つけ、実装の途中で見つかったときだけ止まる。

とらなかった案：

- ライブラリはすべて人が決める：小さなライブラリでも止まると、続けて作れない。条件（無料、ゆるいライセンス、1つのモジュールに閉じられる、データ・認証・お金に触らない）に合うものは、外すのも1か所で済む
- すべてAIが決める：デプロイ先・データベース・認証などは、あとから変えると大きく作り直す。お金もかかりうる

## Claude Code と GitHub Copilot で同じルールを使う

今の形：

- ルールは `AGENTS.md`、スキルは `.claude/skills/` に書き、両方が同じものを読む
- スキルでは `$ARGUMENTS` を使わず、「コマンドのあとに書かれた〜」と書く。両方で同じように読めるようにするため

条件：ルールやスキルを Copilot 用に分けなければならなくなったら、Copilot 用は別のリポジトリにする（人間が決めた）。2026-10-12 の時点では、分けずに済んでいる。

Copilot で効かない守りについては [guards.md](guards.md#copilot-で効かない守り)。

## 判断の理由は、このフォルダに書く

今の形：テンプレートの判断の理由は `docs/template-notes/` に書き、使う側では `scripts/link-template.sh` がテンプレートとつなぐときに消す。

理由：

- このリポジトリの `docs/design.md` などは、使う側のためのひな形なので、テンプレート自身の設計を書けない
- テンプレートのファイルに理由を書くと、使う側に写り、使う側のAIが毎回読むノイズになる
- PR の本文（コミットメッセージ）は使う側に写らない（「Use this template」では履歴が新しく始まる）が、今どの理由が効いているかをたどりにくい。そのため、今の理由はこのフォルダ、経緯は PR と分ける

消す場所を `link-template.sh` にした理由：`.template-version` を書くのと同じときに消せば、最初の PR（立ち上げの PR、すでにあるリポジトリでは `.template-version` の PR）に一緒に入る。`setup-github.sh` ではなくこちらにしたのは、すでにあるリポジトリをつなぐときも通るため。

とらなかった案：

- 理由をテンプレートのファイルの中に、HTML コメントで書く：AIはコメントも読むので、使う側でもノイズになる
- 別のリポジトリや GitHub の Wiki に書く：テンプレートを直すAIが、同じリポジトリの中で読めない
